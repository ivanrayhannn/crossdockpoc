RPA sync flow: GTOPAS first when the part list changes

One parent flow per run ([Sync], [Re-send last Sync] or the Period Rollover). When the run changes which part + destination is crossdock in GTOPAS, the GTOPAS robot runs first and AP POLE starts only when GTOPAS succeeded. When the run changes only quantities or destinations that GTOPAS does not hold, the AP POLE robot starts at once.

Two scenarios

Scenario 1 · GTOPAS → AP POLE

run has GTOPAS rows

The part list of GTOPAS changes: a newly registered part becomes Active (Add), an Active part becomes Inactive (Delete), and a destination added or removed for a part (Add / Delete).

  1. XD06 adds / deletes the part + destination rows on GTOPAS WVJA5204.
  2. GTOPAS succeeded → XD07 uploads EXPORT_PRE → KANBAN → EXPORT_POST to AP POLE.
  3. GTOPAS failed → AP POLE stops: XD07 does not start, the whole run waits for [Re-send last Sync].

Scenario 2 · AP POLE only

run has no GTOPAS row

Only values that live in AP POLE change: Max Case/Day, Pcs/Case, Case/Day of a destination, an order type change of a destination that stays (** → C).

  1. XD06 is skipped (nothing to change in GTOPAS).
  2. XD07 uploads EXPORT_PRE → KANBAN → EXPORT_POST at once.

The parent decides with one query: SELECT COUNT(*) FROM V_GTOPAS_CROSSDOCK WHERE SYNC_DT = :sync_dt. More than 0 → scenario 1, 0 → scenario 2. The staging already writes a GTOPAS row only when a destination appears or disappears for a part, so the count is exactly "the part list of GTOPAS changes".

Power Automate structure

CDX_SYNC_PARENT (cloud flow, in one Solution)
 │  trigger: started by NSP with SYNC_DT, RUN_TYPE (SYNC / RESEND / ROLLOVER)
 ├─ SQL (read-only user): COUNT V_GTOPAS_CROSSDOCK rows of SYNC_DT → scenario 1 or 2
 ├─ [scenario 1 or ROLLOVER] Run desktop flow CDX_XD06_GTOPAS
 │     input : SYNC_DT         output: STATUS (SUCCESS / FAILED), FAILED_ROWS
 │     subflows: Login → for each V_GTOPAS_CROSSDOCK row of SYNC_DT: Add or Delete (MT = DEL) → Logout
 │     a row already in the wanted state (Add of an existing row, Delete of a missing row) = OK
 ├─ Condition: STATUS = FAILED → send e-mail, Terminate (AP POLE not started)
 ├─ [not ROLLOVER] Run desktop flow CDX_XD07_APPOLE
 │     input : SYNC_DT         output: STATUS, FILE, ROW, MESSAGE
 │     subflows: Read views → Build file from the stored template (LLM9Q880 / LLM9Q910)
 │               → Upload 1 EXPORT_PRE → Upload 2 KANBAN → Upload 3 EXPORT_POST → Logout
 │     stop at the first file AP POLE rejects (the next files depend on it)
 └─ Send e-mail (one per run): SYNC_DT, scenario, GTOPAS result, AP POLE result per file

The robots write nothing back to NSP; the result is the e-mail. Child cloud flows need the same Solution; desktop flows called from a cloud flow need the premium / unattended licence of the tenant (to check with the Power Platform admin).

Re-send is safe because both robots set values: AP POLE takes the same values again; GTOPAS treats "already there" and "already gone" as OK. A new [Sync] after a FAILED e-mail is held back by the rule "re-send first", so the last sent values stay the values of AP POLE.
