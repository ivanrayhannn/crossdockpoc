History staging sync for the AP POLE bot

The current history table TB_H_PART_CANDIDATE stays as it is (one row per part + period, overwritten). A new insert-only table TB_H_PART_CANDIDATE_STG_SYNC keeps every change with its own HIST_ID until it is sent. At [Sync] NSP sets SEND_SEQ = number of the upload file and makes the AP POLE upload files (LLM9Q880 Export, LLM9Q910 Kanban) from the stored templates; the bot uploads them in order.

Example part DUMMY-001 (DUMMY PART 001), Pcs/Case 6, Current period 202611 (AP POLE Eff. 11/2026). AP POLE checks every uploaded row one by one: the total Max Shipping Box (RCS) of the Buyer-PD rows must stay ≤ the part's Max Shipping Box Qty.

Two history tables

TB_H_PART_CANDIDATE

existing · kept

History of the parent (Kanban Crossdock Master). One row per PART_NO + PERIOD: a second change of the same part + period overwrites the row. Used for the screen history only, not by the bot.

TB_H_PART_CANDIDATE_STG_SYNC

new · insert only

AP POLE and GTOPAS. One row per changed value (parent or child), inserted by XD05 and by the user's save or upload on the Kanban or the Export Crossdock Master. Rows stay Non Sync until [Sync] sends them. FK (PART_NO, PERIOD) → TB_M_PART_CANDIDATE. The Sync Status, Sync date and run ID of both targets move here: SYNC_STATUS, GTOPAS_SYNC_DT, APPOLE_SYNC_DT and SYNC_RUN_ID are removed from TB_M_PART_CANDIDATE. The screen shows a target Non Sync while the part + period has a row with that target's status 0, else Sync with its latest date.

[Sync] and the bot

  1. [Sync]: NSP takes the rows of each part + period with APPOLE_SYNC_STATUS 0 (Non Sync) and HIST_ID ≤ the last HIST_ID at the click (rows inserted while the run is made wait for the next [Sync]). Key = LEVEL_TYPE + DEST_CODE + ORDER_TYPE + FIELD_NAME.
  2. Per key: AP POLE value = OLD_VALUE of the first row (smallest HIST_ID); NSP value = NEW_VALUE of the last row (largest HIST_ID). Action: no AP POLE value → Add, last row DELETE (NEW 0) → Delete, smaller → Down, bigger → Up, equal → skip.
  3. NSP sets SEND_SEQ = upload file on the last row of each key, 1 Export (LLM9Q880): the destinations of a part whose Max goes down → 2 Kanban (LLM9Q910): every parent change and new part → 3 Export: the destinations of every other part (Max up, new part, or no Kanban row: moves between destinations, deletes, Inactive). Only a Max going down needs its destinations lowered before the Kanban row; everything else is safe after it. AP POLE checks row by row, so inside a file the rows of a part going down / deleted (0) come before the rows going up / added.
  4. In the same transaction: last row of each key → APPOLE_SYNC_STATUS 1, earlier rows → 2 Superseded, all with APPOLE_SYNC_DT, SYNC_RUN_ID, CHANGED_BY / DT. A key that ends on the AP POLE value gets no SEND_SEQ.
  5. NSP makes one file per period + SEND_SEQ from WHERE SYNC_RUN_ID = run AND SEND_SEQ IS NOT NULL ORDER BY PERIOD, SEND_SEQ, PART_NO: the Current files first, then the Next files. File name LLM9Q880_<run>_<period>_1.xls, LLM9Q910_<run>_<period>_2.xls, LLM9Q880_<run>_<period>_3.xls; a file with no rows is not made.
  6. The bot uploads the files in the order of their names and stops at the first failed file (e-mail FAILED names the file). The files of the other period wait for [Re-send last Sync].
  7. GTOPAS: [Sync] (Current) or the Period Rollover (Next) takes every part + period with a row GTOPAS_SYNC_STATUS 0. The bot gets all destinations of the part with CASE_DAY ≥ 1 from TB_M_PART_CANDIDATE_DEST (P/No. + Destination Code, order types together) and compares with GTOPAS WVJA5204: in NSP only → Add, in GTOPAS only → Delete, both → Keep. No SEND_SEQ for GTOPAS.
  8. [Re-send last Sync] runs the rows of the last SYNC_RUN_ID again in the same order. Safe to repeat: the bot sets values, it does not add or subtract.
